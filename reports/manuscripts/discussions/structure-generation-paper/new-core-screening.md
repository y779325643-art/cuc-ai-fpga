## 2. 优先保留的协议候选

暂称“局部架构备选联合选择”，不是已确认的方法名或贡献。

**输入：** 公开需求、允许的结构原语及其可审计属性、接口约束、明确的资源/时序约束。参考RTL、私有oracle、隐藏刺激与最终评价结果不进入选择器。

**流程：**

1. 一次规划调用对每项局部架构决定输出有限的有序备选，每项有稳定ID、局部签名及其依赖。不能把所有字段的笛卡尔积都当作语义有效的设计空间。
2. 程序依据公开规则建立兼容关系与全局约束，选择可行组合；排序只可作为偏好。若使用最小排名和，其数学形式就是普通weighted CSP，不另起算法名字。
3. 将选定组合编译为普通的单一契约/结构骨架，再进行一次行为生成。规划和行为调用均纳入完整成本；本协议没有实现后失败反馈、重新规划或免费修复。
4. 评价方独立检查实际RTL。有限域无解仅说明该候选池未找到解；规划自洽不保证行为、延迟或实际资源合格。

相对原来的唯一结构契约，真正新增的是“提交单一架构前保留局部替代，并允许跨局部选择”。它没有沿用程序区/模型区划分，也没有证明超出既有神经符号合成的理论能力。

## 3. 手工区分案例及其限度

下面是**新的公开规划构造**，不是P01现有任务已具备的能力或已运行案例。

两级多文件乘法工程：`mid=(a*b) mod 256; y=(mid*c) mod 256`。接口为8位，逐笔处理，不考虑输出阻塞时要求总延迟不超过5周期，最多实例化一个指定乘法DSP原语。假定一个公开实现目录提供两个语义等价的局部选项：

| 局部选项 | 指定DSP原语实例数 | 无阻塞延迟 |
| --- | ---: | ---: |
| D：指定原语实现 | 1 | 1周期 |
| L：禁用DSP的两位逐次乘法 | 0 | 4周期 |

两个已有完整提案若分别为`D,D`与`L,L`，前者实例数为2，后者延迟为8，均不满足要求；跨组合`D,L`或`L,D`则在这些假定属性下满足要求。公开条件没有唯一决定答案，端口名或位宽派生不能决定分配。

这里“完整提案均失败”仅指给出的两个提案，不是所有完整赋值均失败。延迟相加依赖串行、逐笔和无阻塞条件；属性必须由可审计实现建立，不能相信模型自行填的数值。当前没有建立或验证该实现目录，没有测量FPGA映射、PPA或最终RTL时序。

**这个例子证明了重组的用途，没有证明新的求解机制。** 同池普通CSP同样能找到两个可行组合。若最终贡献只剩此例与最小排名和，就只能按生成协议的实证价值评估，不能声称新约束算法。

## 4. 必须区分的对照

| 对照 | 共享信息与作用 |
| --- | --- |
| 完整方案选择，不重组 | 使用同一批明确对应的完整提案，检验跨组合是否有用；不能把局部排序同一位置随意拼成“模型给出的完整提案” |
| 逐项首选及固定顺序贪心 | 使用同一缓存局部候选池和公开规则，检验全局选择相对早提交/局部提交的变化 |
| 普通有限域CSP/Sketch | 获得相同候选池、约束、排序、计算预算，允许重组；防止把已有求解器能力算成新贡献 |
| 同池无排序与有排序 | 仅当主张模型偏好有价值时加入；排序不是校准成功概率，也不是PPA估计 |
| 等调用/输出预算的整体规划 | 另做端到端对照，检验生成局部候选池是否优于生成多个整体方案；上述同池消融不能替代此项 |

缓存复用可用于选择器消融，但完整方法对比必须计入池生成成本、未选备选、失败输出及行为生成。有限域中存在可行解不等于模型真实输出经常包含它；手工案例不能代替真实模型pilot。

原M3/M4共享单一HIS的处理变量不能原样沿用：候选池协议改动了规划阶段及信息单位。若选择本方向，需重定P02协议和主对照，原M3/M4仅在明确用途下保留；不能假装只是给原M4增补几行。

## 9. 最有实质内容的领域案例草案：M06配置并发

状态：**供讨论的任务变体与方法设计，不是已采纳的研究定义。** 不改变旧M06及其结果，不迁移旧oracle资格。此案例仍研究首次结构规划，没有引入生成后工具反馈修复。

### 9.1 必须先公开的可观察语义

拟议规则：一笔样本的计算使用该笔样本输入握手时的配置版本。配置通道可否暂时反压是架构自由度；若要求始终ready，就会排除其中一条合法路径。先把配置字段中的权重/偏置/alpha视作计算上下文，`enable`的接收资格含义另列，不混在同一条规则里。

这是新增的公开并发规则，旧一句话需求和串行参考不能替用户作出此决定。同周期配置写与样本握手的先后、复位、在途数量、结果阻塞以及配置字段最后使用时点仍须明确。候选模型得到的是经确认的共同语义和能力说明，不得到旧RTL、私有序列或期望结果。

### 9.2 两类承诺的合法组合

| 配置接收策略 | 运算配置来源 | 在拟议语义下的关系 |
| --- | --- | --- |
| 样本在途且配置仍会被读取时，暂缓接受相关配置写 | live bank | 可以合法：期间没有被接受的覆盖写。必须覆盖实际最后读取时点 |
| 样本在途时仍接受配置写 | 样本接受时捕获的配置/等价已计算上下文 | 可以合法：本笔读取固定版本，新配置供后续样本 |
| 样本在途时仍接受配置写 | 晚于接受时点直接读取可改写live bank | 若存在影响结果的交错写，则不兼容；端口和位宽检查仍可能通过 |
| 暂缓配置写，同时捕获快照 | 快照 | 可能合法但冗余，不能仅因不经济判功能错误 |

手工区分轨迹：先设置配置C0；接受样本A；在A最后一次读取相关配置前尝试写C1。第一种结构应暂缓该写，第二种可以接受但A仍使用C0，第三种可能使A使用C1。这里没有执行或构造私有测试向量；C0/C1只表示两个会影响计算的不同配置版本。

若设计在样本接受时就完成了全部配置相关计算，后续只运输结果，则不必机械地捕获整份配置；它不属于表中“稍后读live”的负例。生成器不能误杀这种实现，也不能把锁定至结果消费当作唯一正确锁定区间。

### 9.3 拟增加的协议机制

局部备选不仅声明端口，还声明“何时接受配置写、何时捕获计算上下文、何时最后读取某字段”等**架构承诺**。程序依据已公开的版本语义导出跨备选兼容义务，先选一个一致结构，再只生成一次行为。

这里的领域内容是检查配置可变区间与事务读取区间是否冲突，而非给两个字段改名。规则本身属于已有并发/接口设计知识；拟研究的是这些义务在备选规划协议中的作用，不能称发明了快照或新并发算法。

规划声明不能保证RTL遵守它。若未来实现，至少要让选定wrapper/接线限制kernel实际读到的配置，保护写入/捕获状态的责任边界，并由独立交错评价验证。现有自由行为孔没有自动提供这些保证。若必须扩展成通用RTL时序证明，本方向不符合最低补工目标。

### 9.4 最小补工与研究影响

- 可复用M06的接口、纯算术参考和模块谱系；数学函数相同不代表并发语义相同。

### 11.2 实例A：现有stream fork的通道来源

| 固定逻辑接收通道 | 完整来源选项0 | 完整来源选项1 |
| --- | --- | --- |
| S0输入通道 | F.out0的data/valid，加S0.in_ready回接F.out0_ready | F.out1的data/valid，加S0.in_ready回接F.out1_ready |
| S1输入通道 | F.out0的data/valid，加S1.in_ready回接F.out0_ready | F.out1的data/valid，加S1.in_ready回接F.out1_ready |

### 11.3 原子分组对结论的影响

另做了压力诊断：将正向data/valid分为G0/G1，将ready分为R0/R1，四组各二选一。fork和join均为16/16端点、方向、文本宽度及当前目标单驱动合法，但只有2/16满足全部8组控制输入下的接受关系；与“一一映射＋ready逆映射”的规则逐赋值一致。全部首选和仅按类型过滤后的首选均失败。

**这不是严格原子通道原型的效果证据。** 拆开同一通道的ready再恢复一致性，可能人为制造用户原规则禁止的错误空间。完整通道边已另行展开验证：每例4种来源组合，2种有完整目标覆盖、无ready重复驱动，且满足接受关系。

两种“固定目标”口径必须区分：

- 若固定的是逻辑接收通道，可选择生产者通道，程序随选项确定性回接ready；这是上表的两组方案。单个选项会改变反向ready的RTL目标端，不能说逐根线目标集合不变。
- 若每组的RTL目标集合也必须固定，且双向通道完整打包，则两条完整straight/cross路由可合成一个二选一组；两选项目标集合相同且都合法。此例不再有跨组选择。

普通first-unused匹配在两组完整通道表示的全部4种偏好配置中，都找到可行组合并达到同样最少备选数。四组压力表示中，forward-first匹配也对全部16种偏好可行，仅2种偏好比联合最优多用2次备选；这是排名代价差异，不是功能/PPA收益。

因此fork足以检验通道来源协议及校验器，**不足以证明一般联合枚举优于简单匹配**。使用成熟匹配算法不自动否定协议贡献，但此例不能证明LLM候选比直接程序装配或整体采样更有价值。

### 11.4 实例B：现有FIR的累加来源

这比交换data/valid别名更接近用户限定的连接问题。来源：[datapath.py](../../../../agent/src/sr2fpga_agent/task_families/datapath.py):2209–2248、:2272–2285。固定三个现有MAC各自的sample/coefficient、ACC_WIDTH、result线、最终结果寄存器及历史状态，只改变三个`accum`来源：

| 固定目标 | 选项0 | 选项1 |
| --- | --- | --- |
| u_mac_new_sample.accum | stage1（previous的结果） | 原有RESULT_WIDTH位全零 |
| u_mac_previous_sample.accum | stage0（new的结果） | 原有同宽全零 |
| u_mac_oldest_sample.accum | stage0 | stage1 |

公开数学草案必须明确固定的三项为`3*sample`、`-2*sample_d0`、`sample_d1`，MAC为无状态、同宽乘加；这些事实来自资产，当前一句话旧需求没有全部公开。不能把模型自报组合属性当可信依赖。三个累加接口均为RESULT_WIDTH（width 8时为11）；全零来源已存在，不新增模块、状态、资源或寄存位置。

符号验证用固定乘积项作为三个独立项，检查组合无环且最终输出中每项恰好一次。8个赋值仅2个满足条件：

- `(1,0,1)`：原链`new → previous → oldest`。
- `(0,1,0)`：`previous → new → oldest`。

全部首选`(0,0,0)`使前两MAC成环；按最少备选数选`(0,1,0)`。MAC没有中间饱和或舍入，固定同宽加法允许这两种次序；脚本核对原始局部表达式并作符号依赖检查，没有执行FIR RTL或全时序功能评价。

附加诊断：只检查当前前缀无环、不能回退的贪心，在8种人工偏好配置中有2种会先选出两个零根，最后无法覆盖全部项；联合检查可找到合法链。但普通覆盖传播或直接比较两种合法次序也可解决，不能以这个弱贪心结果声称新算法必要。

**关键复用缺口：** 三个MAC、stage0/stage1/filtered_result及sample_d0/d1均在fir_filter_core内部。当前骨架只提供该组件的自由行为孔，尚未冻结内层实例、声明与状态责任。必须先支持固定这部分已有结构并只开放三个accum槽，才能成为当前框架的合法原型；否则停止使用此例，不允许模型在行为区自行改链后宣称程序固定了结构。无需增加新算法或新状态，但这不是零补工。

## 13. 新目标下的模型实测与条件性模块责任候选

最新目标已经授权SCI初稿和必要本地实验。用户另明确让Codex子agent直接作被测模型；[首轮记录](native-codex-development-pilot.md)保留实际两份首次输出、独立评价、原生隔离限制和模型配置证据。两份在同一公开TD开发任务均通过有限功能检查，不能据此声称提示定位改进或新方法有效。

本轮新问题是：**外部函数正确、实例/端口存在，是否足以证明实现遵守了明确声明的条件性计算责任？** 这里不是将程序区和模型区混合划分，也不继续连接候选搜索。

设父模块为`P(x,z)`，子模块正常输出为`z=f(x)`。普通功能检查只验证`P(x,f(x))=F(x)`。如果需求额外明确规定在guard成立时父输出直接委托给子模块，则本次候选采用更强的公开合同：对自由边界`z`，guard下`P(x,z)=z`，其他模式按其声明的独立规则。边界干预只是检查这项已声明合同，不是从普通功能规格自动推导它，更不能把off-manifold不符合当普通功能缺陷。

**已有机制与潜在增量：** [Feng/Hu 2005原文PDF第1–2页](https://www.cs.ubc.ca/~ajh/mypapers/2005FH.pdf)已用新primary input替换切点，并明确可能产生false inequivalence；本地Yosys也已有`cutpoint`。因此自由边界、黑盒替换不是新算法。CPPL §III-A的结构定理只投影层级，其DCE会删除未使用实例；HINT §3明确不声称内部结构等价；HierSVA已有vacuity/faithfulness/mutation。可继续研究的窄变量只有：如何将生成前明确的条件性责任承诺转成独立、不过强的检查，以及它相对简单存在检查/严格构造是否有边际价值。不能把前述工作中的合法优化叫作工具缺陷。

**已执行的资格诊断：** [公开合同与四个控制](../../../../artifacts/guarded-responsibility-qualification-20261021-01/public-spec.md)、[完整结果](../../../../artifacts/guarded-responsibility-qualification-20261021-01/results.md)。新建4bit ALU公开fixture，父层在非加法模式需要原始a/b；常规委托、父层重算、fake-use抵消、合法交换子模块输入四者均通过1024项普通功能穷举。责任检查中，两委托实现各16384项全过；重算/fake-use各3840项不满足额外合同；force/release工具守卫全过。负控制非零退出码保留。这些是手写控制，不是LLM错误率或CPPL复现。

**强反证已实际核对：** [第二次独立run](../../../../artifacts/guarded-responsibility-qualification-20261021-02/results.md)新增wrong-mode控制，常规1024项全过，责任干预7680/16384失配；其在减法模式真实使用加法器、加法模式却父层重算。五次Yosys保持层级的proc/opt/opt_clean后，adder4实例数依次为正常1、重算0、伪使用1、交换1、错误模式1。原4fixture不重跑，全部原件hash未变。由此可确认该序列后的实例存在检查不足以保证明确的条件性责任，但不能泛化到所有DCE。固定父层mux或足够强的typed IR本来就能保证委托，不能预设检查器超越它们；若严格构造完全解决问题且没有保留父层自由度的实用需求，则本候选研究价值仍不足。
