## 1. 真实公开线索及其解释边界

UART 公开 [legacy design-goal 摘要](../../../../agent/src/sr2fpga_agent/project_generator.py#L2945)为接收字节按序缓存发送、不丢不重；[catalog](../../../../contracts/task-catalog/sr2fpga-task-catalog-v0.2.json#L846)只有 frame/order/no-drop 义务标签。实际 [top/FIFO](../../../../agent/src/sr2fpga_agent/task_families/protocol.py#L797)提供 RX 串口而无 ready，FIFO 深度 4，`tx_enable` 关闭时不发起读取，[满时写使能会屏蔽新字节](../../../../agent/src/sr2fpga_agent/task_families/protocol.py#L833)。

与 engineering_status 核对并读取了公开入口：[默认 assumptions](../../../../agent/src/sr2fpga_agent/project_generator.py#L701)只有单时钟、无 vendor IP；[实际需求文本入口](../../../../agent/src/sr2fpga_agent/requirement_envelope.py#L411)优先 `request.description`；摘要还被 [`_test_pass_means`](../../../../agent/src/sr2fpga_agent/project_generator.py#L3044)包装成测试说明。未定位到 UART 专属的速率、最长关闭、overflow 丢弃许可或“received 仅指未满时接受”定义。

因此，本卡不宣布原任务已坏：摘要不是完整的 forall 协议。可严格否定的是**一项明确的强化解释**：“全部待发容量只有 4 字节；RX 不可暂停；tx_enable 可无限关闭；每个合法接收帧都必须保留。”当前旧任务究竟要求这个解释，仍是语义待定，不能由参考 RTL 的满屏蔽来替用户采纳丢弃许可。

对照模式为[公开 ready/valid streaming intent](../../../../agent/src/sr2fpga_agent/project_generator.py#L2982)与[两个 elastic stage 的实际构造](../../../../agent/src/sr2fpga_agent/task_families/stream.py#L116)。存在输入 ready，可以停止接受新 beat；这与 UART 的不可反压物理 RX 不同。也不能据此默许修改旧任务的固定周期、单级或全部外部握手含义。

## 2. 候选目标与三种真正可区分的结果

目标不是提高原生功能全通过率，而是避免生成器承诺不可能架构，或把建议环境条件悄悄变成“原需求”。三态的判断对象必须完整注明：**哪份需求解释、哪些已采纳前提、哪一个结构计划及能力模型**。

| 结果 | 具体公开模式/分析实例 | 能与不能得出的结论 |
| --- | --- | --- |
| 可行，限定于明确前提和保证 | ready/valid 的输入接受定义为 `in_valid&&in_ready`；两个正确 elastic stage 在满时撤销 ready。若保证只要求已接受 beat 的顺序、不丢不重及输出 stalled 时保持值，可在任意 out_ready 停顿下保持安全性 | 可以证明所述抽象计划的安全保证可满足；out_ready 永不恢复时不能证明最终输出，不能把安全性当活性，也不等于生成 RTL 已正确 |
| 不可能，有有限见证 | 上节 UART 强化解释、初始空、tx_enable=0；连续送入 5 个合法帧，而 TX 退休数为 0。4 个待发槽无法继续接纳第 5 个任意字节 | 在该解释和全部待发容量=4 的计划中不可满足“不丢每个物理 RX 帧”；这是结构能力矛盾，不是某模型 RTL 功能失败，不是对旧任务全部解释的判决 |
| 待定，保留缺口与未采纳条件 | 当前 UART 摘要未定义 received/overflow/速率/最大停顿；或某新 native profile 只给最大吞吐、没给最小服务保证 | 不替用户选择“只保证 accepted bytes”；不因没找到反例判可行；可报告某组充分条件的推导，但其 adoption 仍为未采纳 |

第 2 行的见证在事件层是 `q:0→1→2→3→4`，然后第 5 次 arrival 无空槽；5 个 UART 帧可以按正常串行帧间隔到来，无需不合法地同周期到达。这里只作静态容量论证，没有生成波形或执行 HDL。若计划还允许 prefetch/holding 等存储，必须先计入全部待发容量 C，见证改为 C+1；不能仅凭“FIFO4”忽略其他储存，也不能偷加寄存器却继续声称同一结构能力。

主审随后完成了独立的[数学资格控制](../../../../artifacts/responsibility-capacity-assumptions-static-20261021-01/README.md)：明确假定抽象总容量C=4、一个零服务窗口，穷举5种初始占用与64条六事件到达轨迹，共320条。满足窗口到达上界`4−q0`的129条均不超容量；其余191条给出超容量前缀。空队列的五次到达见证已单独核守恒与首个违规前缀；另核17个符合信用接纳规则的单步转换均保持容量界。此处C=4是手工资格控制，不是对真实UART总容量的断言。只执行纯Python数学，无UART波形、HDL、模型或真实任务评分；信用单步安全也不证明生成RTL、顺序或活性。原始执行与结果保留，不增加模型分母。

## 3. 最小新增处理：前提不能在跨阶段时被升级

### 3.1 输入 → 程序 → LLM → 输出

| 环节 | 最小内容 |
| --- | --- |
| 公开输入 | 实际需求原文及 locators；显式环境约束；可信库的有限能力 profiles；允许的结构备选范围。最多两项局部备选即可，不要求大候选池 |
| LLM 计划提议 | 声明可用局部结构/protocol mode、容量、服务能力及对应来源；允许明确写 unknown。模型不能把自己提出的速率假设标成用户已给，也不能把库名当行为证明 |
| 可信程序 | 解析允许的能力字段，建立容量/接受/退休模型，组合局部前提，求证保证或生成合法见证；必要时生成输入环境上的候选条件，并标记其来源、必要/充分性质与未采纳状态 |
| 确认边界 | 只有已有明确公共条款或以后获准的条件才进入已采纳前提。新建议不自动采纳；本轮不要求用户确认，也不把研究设计当成采纳动作 |
| 生成前冻结 | 保存已采纳条件、计划身份、模型版本、局部义务和证据依赖；待定计划不能以“可行计划”进入结果。条件未确认时，可以交付诊断，但不能靠删除条件外输入取得成功 |
| 首次行为生成 | LLM 一次生成已冻结局部行为；取得同一允许信息。之后检查实际 RTL 是否兑现能力/profile，工具反馈不回送修复；计划可行不替代实际实现验证 |

### 3.2 与已有 provenance 的区别

仓库 [`build_requirement_envelope`](../../../../agent/src/sr2fpga_agent/requirement_envelope.py#L252)已经区分 explicit/default/unknown，并接受 assumptions/clarifications。新增 `origin` 字段不是方法贡献。

可检验的最小规则是：**由设计能力推导出的环境限制必须继续带着“未采纳”的依赖标记，不能在规划、生成 prompt、验证 assumptions 或汇总分母中自动变成需求。** 例如“最多四个到达再暂停”即使由程序证明足够，也不是从“FIFO4”推出的环境事实。

计划还应保留两项不可混淆的内容：

- `required_environment`：为了某保证而推导的条件及其证据；可能未被允许。
- `adopted_environment`：实际已有权威依据或获准的输入域；决定可使用的生成/验证上下文。

这是概念接口说明，不是新增注册 schema 或替换既有状态格式。若以后实现，需复用/扩展已有契约机制，不能另造平行的正式结果体系。

还须区分逻辑强度：设已采纳环境为A0、某已知充分前提为Areq，使用该组件合同时须证明`A0 ⇒ Areq`，而不能默默把输入域改为`A0 ∧ Areq`。若蕴含未成立，只能说明该合同尚不能认证计划；Areq可能过强，并不自动证明所有实现均不可能。只有对明确计划/精确模型给出可映射的违规见证或不可实现性证明，才使用“不可能”。未知字段、保守摘要及未闭合证明均保留待定。这个refinement规则是标准合同推理，拟研究的是它在生成交接中的实际落实。

### 3.3 最小概念接口字段

只需覆盖本轮两模式，不建设通用架构语言：

```text
requirement:
  guarantee_kind: safety | liveness | deadline
  counted_input_event: physical_rx | ready_valid_accept
  statement_locator, interpretation_id
environment_fact:
  predicate, origin(public|library|proposal), locator
  adoption(existing|explicitly_accepted|unadopted), derivation_dependencies
```

`library` 表示可信组件在其前提下的保证，不是库对外部环境的授权。LLM 提议某能力不能自行成为可信事实；未通过库引用或后续实际模块验证前，只能按承诺能力评计划，保留实现义务。源码/文本 locator 的存在也不证明语义蕴含，需要核对或独立资格。

## 4. 容量与服务规则：足够小，但必须精确

令 `a_t` 为物理合法 RX 到达，`i_t` 为系统实际接受，`d_t` 为从待发队列退休到 TX 的 token，`q_t` 为尚未退休的全部待发 token。UART 参考策略是满时拒绝输入，概念上：

```text
i_t = a_t and (q_t < C)
q_(t+1) = q_t + i_t - d_t
no_loss_of_physical_rx: for every t, i_t = a_t
```

同拍读写、退休和到达的判定顺序须随 native/系统契约给出。参考 RTL 使用前状态 full 屏蔽写，不能只证明 `q+a-d<=C` 就悄悄允许满时同拍读写交换；否则改变了原接纳集合。

ready/valid 模式的被计数输入本来是 `i_t=in_valid&&in_ready`，拒绝继续接受是接口机制；不能把 UART 的 a 重命名成 i 后声称无条件 no-loss。反过来，ready/valid 对未被接受 beat 的最终处理仍取决于源是否按约定保持/重试，不能替外部源承担未经声明的行为。

服务契约必须是**可依赖的最小服务/最大等待保证**，并注明适用条件。只有“最大吞吐可达 μ”不保证任何时候真的服务；`tx_enable` 有时为 1 也未必提供足够的服务窗口。

候选条件可以给必要条件和充分条件，但不得混同：

- 必要线索：任何无退休区间内，初始空余 4 槽不能容纳超过 4 个到达；它不是完整的长期充分条件。
- 一个非最弱的充分条件模板：初始空；每轮 burst 最多 B≤4 个有效 RX 字节；burst 后没有新到达，并保持服务使能至少一个已获保证的 drain 窗口；库合同保证在该窗口内退休 B 个字节。之后才能开始下一轮。这是输入流量/使能的建议，不是当前已有约定。
- 单独限制最长关闭时间不一定够：打开期间服务可能追不上平均到达；单独给平均到达率不一定够：突发仍可超过容量；只说最终 enable/ready 恢复也不足以给有限等待界。

不能以“队列永远不满”直接充当外部前提来证明不溢出；应尽可能给输入可核查的到达/使能约束。若残余条件仍依赖内部 q 或设计输出，必须明确它不是环境可独立承诺的输入条件，不能无声采纳。所给条件还应非空、允许有意义的到达；“永远无输入”可使一些逻辑命题成立，但不得包装成原任务已解决。

## 5. 纯标准工具的同信息强基线

本轮核对 [Pacti 官方 getting started](https://www.pacti.org/docs/getting_started/)：它已有 assume-guarantee 接口、组合、refinement、quotient 和不兼容诊断的具体 API 示例。输入前提与输出保证有明确变量范围，能够从已有合同计算组合或缺失组件合同。**不能声称新的 contract algebra、前提组合或残余条件推导。** 官方论文 PDF 此次返回 403，未将其未读细节升级为证据；未安装/运行 Pacti。

公平强基线至少包含：

1. **同一有限事件模型加标准模型检查/SMT。** 输入相同 C、全部 storage、接受/退休规则、服务与环境范围；用整数状态转移或有限自动机检查安全性，产生同样的 q 见证。超时、模型缺失或不支持应为 unknown，而非“不可实现”。本轮只设计该基线，未运行它。
2. **Pacti 式标准合同流程。** 对可表示的到达/服务计数或线性界，获得同一已形式化条件，做组合、refinement 或 residual/quotient 分析。它的线性合同示例不能直接当任意 UART 无限时序的完整证明；将时序封装为 sound 服务摘要的工作两边都要计入。
3. **标准工具加同样的 provenance/adoption manifest。** 给一个普通 planner/脚本同样的来源与确认状态，让其保留 proposed/accepted、冻结并向生成/验证传递。这是对协议贡献最强、最直接的对照，不能只比“没有记条件的裸 prompt”。

完整 IR 明写环境模型/队列控制后也能检验同一问题，应记录其形式化成本；但若一个更小的标准模板即可完成，不能故意只选完整手写 FSM 来制造省工。纯标准工具不需要 LLM 提出能力备选；LLM 在这里最多贡献从原文/库材料提出有限的合法备选和证据定位，而非替换可信可行性计算。

## 6. 是否比旧简单协调多了可保留的交接增量

有一个值得裁决的具体增量：旧连接/分区题的公开函数、接口和图已充分给定，程序只需选一个正确构造；本问题则必须同时决定**是否有满足原承诺的构造，以及所需前提是否已获准**。一个“正常语法、端口、局部函数均可实现”的计划仍可能全局不可能；程序还需把不可能见证或未采纳条件交回，而不是生成一个缩小需求域的候选。

但这不是仅靠新顺序就成立的方法。系统级假设应限定为：

| 可反驳的交接收益假设 | 需要与标准基线比较的实际证据 |
| --- | --- |
| 单一计划记录避免未采纳前提漏进 candidate prompt 或 verification assume | 预先定义的来源/采纳状态变体；输出上下文逐字段核验；不得读取 hidden 内容来补条件 |
| 自动派生需要的流量/停顿条件，少写一份人工规则 | 同一事实/能力输入下，用户真正录入的条件、模板、映射与审阅步骤；条件在标准工具中是否同样自动得出 |
| 可行/不可能/待定在交接后保持一致，避免把规格矛盾算模型失败 | 有限 witness 的独立回放或静态重算、服务摘要资格、unknown 原因和实际实现义务；不是只核 JSON 格式 |

这些收益均未测量。本轮“保留”只表示值得做一次明确同信息 baseline/接口设计裁决，**不表示协议贡献已建立，更不表示允许进行模型实验**。如果标准工具加一个简单 manifest 已完成全部交接，且不增加人工负担，则该方向是工程整合；不应为了 SCI 再建一个语言或增加候选调用。

## 7. 域边界、最小规模与停止条件

最小范围为：单时钟、固定有限容量、按序、无取消/重发、UART 物理不可反压或 ready/valid 接受两类模式；服务摘要来自明确公开条款/可信库，最多两个局部备选。不扩多时钟、统计丢包、网络拓扑综合、最弱环境自动合成或无界异步协议。

应立即停止或保留待定，而非继续自动补条件的情况：

- counted input、overflow、reset 或 guarantee 的安全/活性含义未定，且会改变结论；当前 legacy UART 属于这一限制。
- 只有模糊吞吐上限，不能给 sound 服务保证；后端不能表达实际 simultaneous-event 规则；或容量清单缺 pending/held/storage。
- 推导条件只能循环地写成“系统不失败”，或需要禁止全部有意义输入。
- 所谓新增步骤与标准合同分析加同一 manifest 完全一致，且无交接正确性/工作量的独立差异。
- 不可行见证只针对一个有限候选池，却被宣传成所有可能架构均不可能；条件外样本被静默移出原分母。

即使以后明确采纳新环境条件，也须新修订记录其改变的输入域，保留旧问题与不可行解释，不把被排除困难条件下的样本转换为首次生成成功。计划静态可行、组件兑现能力、最终 RTL 满足普通功能，是三个分别需要证据的层次。

本轮没有采纳任何新环境前提，没有登记新 schema/status，没有生成行为或评估候选。交付是一张带真实需求缺口、标准工具强对照和停止条件的方法卡；不是原任务缺陷裁定、生成收益结果或官方研究规则变更。
