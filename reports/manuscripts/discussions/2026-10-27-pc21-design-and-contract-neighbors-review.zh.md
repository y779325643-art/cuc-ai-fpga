# PC 2.1 设计审查与契约近邻对比

日期：2026-10-27。路线 A，分支 `codex/paper1-ai`，HEAD `e20dfd2ce46c5690767e30cb629fb5c58aff073a`；审查对象包括当前未提交实现，不能将结论归属于该提交本身。

本次阅读 PC 2.1 规范、注册 schema、当前 checker／emitter／development 代码，并用纯 Python 独立复现一项构建缺陷。近邻核对以指定版本论文正文及附录为依据，不代表重新审计了这些工作的实现。未运行候选模型、HDL 实验或完整回归；未修改 PC 实现、评测器和研究定义。

当前 PC 的核心是：**把跨模块的表示、连接和实现责任表达为可检查契约，再将接受的设计转成工具拥有的工程结构与模型填写的行为接口。** 量化张量语义使它超出普通端口清单；保留直接 RTL 行为实现，使它区别于完整可执行算法 IR。

## 1. 当前设计在哪里、包含什么

- 表示设计：[PC 2.1 设计文档](../../../docs/specs/PC-2.1-AI-stream-contract-design.zh.md)。其开头 2026-09-15 的“尚未落地”核查是历史时点，当前能力应结合代码判断。
- 注册格式：[design-proposal](../../../contracts/pc/2.1/design-proposal-2.1.schema.json)、[project-contract](../../../contracts/pc/2.1/project-contract-2.1.schema.json)、[behavior-bundle](../../../contracts/pc/2.1/behavior-bundle-v1.schema.json)。
- 使用入口：[当前 PC 开发说明](../../../agent/src/sr2fpga_agent/pc/README.md)。旧 System-HIS／PC 2.0 文件不是当前设计。

| 层次 | 当前内容 | 起到的作用 |
| --- | --- | --- |
| 可信公开输入 | requirements、target、capability 的原始字节绑定；顶层接口取自 requirement boundary | 模型不能自行替换外部接口和任务来源 |
| 项目结构 | 模块、结构／行为分类、参数、时钟复位域、实例与网络 | 检查引用、展开、方向、驱动与类型兼容；确定性生成结构 |
| 张量与传输 | shape、element、scale／zero-point、per-axis、遍历、lane／mask、dense／partial-sum 序列 | 区分同位宽但不同含义的连接；派生 beat 类型及拍数 |
| 局部实现义务 | state、numeric／timing、七类 tensor relation、buffer rule、requirement map | 检查有限声明关系，记录需要后续验证的责任 |
| RTL 准入 | 固定头部、实例、连线和文件；模型仅提交 body；解析与构建版本绑定 | 限制修改范围，拒绝结构越权与不匹配的旧行为包 |

关键例子：两个流都为 18 bit，不代表它们可以直连。布局不同、量化尺度不同或部分和顺序不同，会改变数据含义；PC 检查展开后的语义类型，而非只比位宽。转换必须成为明确的行为模块，构建器不会自动补上算法。

## 2. 审查发现

### 2.1 P1：内部线名拼接存在碰撞，直接影响结构构建保证

[emitter.py](../../../agent/src/sr2fpga_agent/pc/emitter.py) 第 216 行使用 `w_{child_id}__{physical_port}`。合法标识符允许下划线，因此该拼接不能唯一编码二元组。

两个合法端点——实例 `x` 的输出 `a__p_b`、实例 `x__p_a` 的输出 `b`——都会变成 `w_x__p_a__p_b_signal`。用两个独立 identity 叶模块构造 PC 后，`check_design` 和 `build_structure` 均接受，输出包含：

```verilog
wire [7:0] w_x__p_a__p_b_signal;
// 两个子实例的不同输出都连接到这个名字，wire 也被声明两次。
assign outA = w_x__p_a__p_b_signal;
assign outB = w_x__p_a__p_b_signal;
```

主代理独立复现结果：`duplicate wires: {'w_x__p_a__p_b_signal': 2}`。这是构建器把原本独立的网络合并，不能归因于候选行为错误。本次没有执行该例的 HDL compose／仿真，因此不推断下游工具最终拒绝还是接受。

建议优先修复为稳定哈希或长度编码，并在整个模块命名空间检查端口、参数、wire 与实例名冲突；用对抗性合法名字验证原图的端点关系被保留。这比立即扩大模型实验更直接关系到核心机制是否成立。

### 2.2 需求映射表达来源与覆盖，尚不证明事实被正确解释

[checker.py](../../../agent/src/sr2fpga_agent/pc/checker.py) 第 180–182 行检查 fact ID 与角色；第 392–418 行检查映射对象和必需覆盖。它没有证明某个 guarantee 的内容真的表达了 reset、frame 或某项数值规则。

因此，引用合法公开 ID、把所有义务映射到一个模块，并不等于解释正确；内部两端共同声明错误尺度，也可能通过相等检查。这是 schema 已注明的设计边界，不应列作未实现的完整语义证明 bug。可以优先为少量关键事实补充机器可检查的类别和值绑定，使诊断更有针对性。

### 2.3 `compute` 的自由度会改变实际约束强度

[tensors.py](../../../agent/src/sr2fpga_agent/pc/tensors.py) 第 124–185 行对 identity、fork、repack、requantize、zip_add、reduce_sum 检查具体兼容关系；`compute` 则保留端口、方向、域与 fact 引用检查，将算法留给行为实现。

候选可以选择细分模块，也可以用一个较大的 compute 覆盖大量端口。这是规范明确允许的通用性选择。实验应记录候选结构粒度及有限关系／compute 的覆盖范围，否则不同样本虽然都“使用 PC”，实际接受的静态约束并不相同。

### 2.4 行为义务、执行诊断和修复路由尚未完整连接

[checker.py](../../../agent/src/sr2fpga_agent/pc/checker.py) 第 69–74 行将实际张量／算术、背压、复位、state 实现、活性和时序列为 deferred；[tensors.py](../../../agent/src/sr2fpga_agent/pc/tensors.py) 第 182、202 行输出 `not_evaluated` 义务。AST 准入已经限制结构和写入范围，但不会由此证明计数器、FSM、复位生命周期或数值实现正确。

当前 DW→PW 有独立手写参考及执行检查；它不是通用 PC 自动生成的监视器。[development.py](../../../agent/src/sr2fpga_agent/pc/development.py) 第 147 行接受 `repair_design`／`repair_behavior` 标签，也不等于已经实现自动归因、路由和迭代控制器。

这使“义务 → 公开检查／诊断 → 可修改层级”的连接成为后续最有价值的补齐点。协议、控制、RTL 语义及算法错误都可以进入机制实验，但需要逐项区分：静态拒绝、构建避免、运行时发现、反馈修复分别由谁完成。

### 2.5 当前版本绑定是全局失效，尚非最小依赖重建

[emitter.py](../../../agent/src/sr2fpga_agent/pc/emitter.py) 第 158–169 行把整份 design、公开来源、能力、代码和工具身份纳入每个 unit key；第 433–439 行要求行为包绑定完整构建计划。无关模块或 intent 文本变化也会让全部 unit ID 改变。

这种保守策略能防止新契约误用旧行为，代价是重建范围大。当前适合称“版本绑定与保守失效”；局部语义依赖缓存可作为后续优化，不必成为首篇机制论文的前置条件。

## 3. 与四项直接近邻的区别

| 工作 | 契约／IR 的内容和执行方式 | 与 PC 的具体区别 |
| --- | --- | --- |
| [CPPL v1](https://arxiv.org/html/2605.17892v1)，§III-A–D | 用户 Python DSL 声明结构，LLM 输出 JSON 电路操作；前端展开层级与实例、检查类型和连接，经 CIRCT 产生 RTL，并用诊断重试 | PC 允许模型规划项目结构，并检查量化张量／事务边界；随后仅机械生成结构，算法仍以模型 RTL body 实现。确定性连线本身已有先例 |
| [HINT v2](https://arxiv.org/html/2608.07625v2)，§3 Table 1、§4.1 | 模型生成可执行硬件意图，包含类型化事务、持久实例、状态所有权、reset／commit、进度与资源复用；先执行验证，再落实 RTL，架构改变返回上游重验 | HINT 更深入算法和状态演进；PC 聚焦工程边界、有限关系和实际结构产物。PC 的特征在结构所有权、body 准入及版本绑定的结合。HINT 的 step 不必等于一个 RTL 时钟周期 |
| [VeriRefine v1](https://arxiv.org/html/2607.18519v1)，§3.3–3.5 | 每信号 ASTF 固定组合／时序类别、时钟复位、有优先级的条件—动作及规范引文；schema 与五层审计后生成 RTL，区分理解错误和代码错误 | ASTF 把信号行为解释显式化；PC 把多模块连接和边界关系显式化。PC 不要求完整表示每个状态转移，也因此不能静态覆盖同等粒度的行为问题。分层修复已有先例 |
| [Veri-Sure v2](https://arxiv.org/html/2601.19747v2)，§3.1–3.3、附录 B | Architect 生成接口、时钟复位、输出延迟、功能／corner cases 等 JSON 契约并 lint；波形追踪和依赖切片指导块级补丁与回滚 | Veri-Sure 根据故障依赖决定哪些块能改；PC 根据结构／行为所有权决定哪些对象能改。两种边界可以组合，不能把“限制模型编辑范围”本身作为首创 |

以上几项最接近的部分分别是结构编译、架构意图、分层修复和受限编辑。它们不只是“加一份契约提示”。尤其 HINT 已有状态所有权与上游重验，VeriRefine 已有表示／代码两层修复，比较时应承认这些交集。

当前可成立的区别是组合及作用对象：**量化流式 AI 的语义边界类型检查，接受后确定性工程构建，以及绑定该契约版本的行为填写权限。** 完整诊断关联与自动修复路由还需落实；不能把阶段标签当成完成证据。

## 4. 对机制验证论文的直接建议

不必要求每个组成部分都是首次提出。更合适的是围绕以下可检验命题组织开发与实验：

1. **前置检查：** 对同位宽、不同布局／尺度／partial-sum 顺序的声明错误，检查能否在 RTL 前拒绝；同时保留合法变体测误拒绝。双方同时写错且相互一致的案例，用来显示静态比较和任务验证的分工。
2. **结构保持：** 给定同一有效 PC，对比自由完整 RTL 与骨架＋body；观察连接、接口、文件一致性以及修复引入的新结构错误。先修好并验证命名碰撞。
3. **行为修复：** 固定同一个失败工程及编辑范围，对比原始公开反馈与关联到义务／模块的反馈；覆盖握手、off-by-one、复位和数值错误。这样才能把诊断效果与限制编辑范围的效果分开。
4. **契约变更：** 进行一次合法设计修改，验证旧行为被拒绝，并走完更新行为后重新执行的过程；同时记录当前全局失效造成的重生成量。

人工故障可作为上述机制验证的主体，小量真实模型轨迹补充实际可用性；这些设计建议不构成本次已执行的结果。复现近邻时还需统一候选可见信息：例如 Veri-Sure §3.1 在有参考 TB 时允许交叉核对接口与时序，不能把不同信息条件下的论文成功率直接作为对照。

这条论文路线能够形成清晰论证：契约提前暴露哪些错误，骨架保持哪些决定，反馈如何帮助修复剩余行为错误，以及三者协同的成本和边界。
