## Confirmed decisions

### D1. Research narrative and hierarchy

The v1.8 deterministic-generation and bounded-repair line becomes the foundation
and secondary evidence for v1.9 rather than a competing primary hierarchy. The
narrative is:

```text
requirement-to-project uncertainty
→ typed contract and deterministic project construction
→ one auditable project can be generated/recovered
→ single-point generation does not explore alternative legal architectures
→ explicit design-space construction and real QoR feedback
→ contract-guided evolutionary exploration
```

The paper must not claim that deterministic generation caused poor performance.
The supported gap is the absence of systematic multi-architecture exploration
and tool-feedback-based selection.

- Primary: RQ1--RQ4 for DSC/search/hidden/physical-cost evidence.
- Secondary: SRQ1 deterministic project foundation and SRQ2 bounded recovery.
- Requirement-boundary behavior remains a qualification layer rather than a
  competing primary RQ.

### D2. System identity

SR2FPGA is designed as a **Hardware Code Generation Harness**. It orchestrates
requirement completion, candidate RTL/project generation, deterministic project
assembly, verification, implementation tools, repair, evolution, evidence, and
lineage. The word `Harness` itself is not novel because HORIZON already uses an
executable hardware-task harness/project-pack framing.

### D3. Requirement completion before DSC

A user's natural-language request is not treated as a complete frozen
Requirement Envelope. The Harness separates:

- `explicit_hard`;
- `derived_hard` with a recorded derivation;
- `proposed_default` exposed for acceptance/replacement;
- `design_variable` for implementation freedoms;
- `unresolved_semantic` requiring clarification or separate assumption branches.

Immutability follows acceptance and provenance, not mere presence in the initial
request, seed FPP, target profile, or tool output. Seed structure and measured
QoR are observations, not user requirements. Interface, width, precision,
protocol, timing, and target facts become fixed for a search block only when
explicit/accepted/necessarily derived. Different externally observable semantic
branches cannot be mixed as functionally equivalent Design Points.

If the user provides no scalar preference, the Harness preserves a Pareto set
instead of inventing a hidden weighted objective.

### D4. Outcome state model

The system does not use one top-level `capability_gap` terminal state. A clear
request may still yield a candidate when downstream evidence is unavailable.
Every attempt records independent axes:

- `generation_status`;
- `requirement_status`;
- `verification_status`;
- `implementation_status`.

Unavailable evidence limits credit and may make a confirmatory comparison
`not_assessable`; it does not erase a generated candidate or convert text
generation into verified delivery.

### D5. DSC origin and meaning

The LLM proposes a DSC before official search from accepted observable intent,
provenance-bearing engineering defaults, a verified seed FPP, a selected target
profile, and permitted public tool facts. The DSC exposes architecture freedoms,
domains, constraints, edit boundaries, evaluator commitments, and objectives.
All comparable search policies consume the identical frozen DSC.

`DSC-valid` means structurally well-formed, bounded, and consistently mapped to
declared evidence. It does not prove that a concrete RTL candidate is correct or
that the design space contains a global optimum.

### D6. Evolutionary realization and repair

The main search does not require a family-specific RTL template for every
architecture. A Design Point seals:

- semantic architecture decision;
- concrete RTL patch;
- parent/public-feedback provenance;
- Project Contract and child FPP hashes;
- complete lineage.

The LLM emits semantic decision and concrete patch together as the mutation
operation; a second stochastic realization call for the same Design Point is
not used. Registered deterministic transforms may be reliable fast paths but are
not the only generation route.

EA is defined by population, inheritance, public fitness, parent selection,
survivor selection, diversity retention, and Pareto archive. Mutation-only EA is
the minimum method; RTL crossover is not required.

Architecture mutation starts from a public-feasible parent to explore QoR.
Bounded repair starts from an eligible public-failing child to restore accepted
functional/protocol/tool obligations. Repair creates a new child, never erases
the failed parent, consumes the common budget, cannot use hidden information,
and must pass full public re-evaluation before population entry.

### D7. Verification/UVM boundary

DSC is not RTL and is not simulated by UVM. UVM supplies a useful architecture
for verifying realized candidate RTL/FPPs:

```text
sequence item / sequence
→ driver
→ candidate DUT
→ passive monitor
→ predictor/reference model
→ scoreboard + protocol/timing assertions + coverage
```

Requirement completion and DSC qualification happen before realization. The
verification environment maps accepted obligations to observable checks and is
applied only after RTL exists. Current Icarus/Python oracle infrastructure may
implement UVM-style responsibilities without requiring the complete UVM class
library; a full UVM backend is a later tool choice, not a current requirement.

### D8. Mathematical/design-theory stack

The accepted minimum theory stack is:

- assumption--guarantee contracts;
- finite-domain constrained DSC space;
- feasibility-first Pareto/NSGA-II-style selection;
- CEGIS-inspired bounded public repair.

Synchronous Dataflow balance and FPGA Roofline may be task-specific derived
constraints. MAP-Elites is not in the minimum method and should be considered
only if ordinary Pareto search demonstrably collapses architecture diversity.
The equations and references are recorded in the candidate and canonical
citation registry.

### D9. DSC adequacy authority

No single authority proves architectural completeness.

- The user owns intent and preference authority.
- At least two independent hardware experts create a presealed bounded
  architecture-opportunity reference before seeing the LLM DSC.
- After the DSC is sealed, blinded mapping estimates weighted opportunity recall
  and proposal validity.
- Proposals outside the reference receive open-set adjudication as valid novel,
  invalid, duplicate/rephrased, or not assessable.
- Rater agreement and third-party adjudication are reported.
- A fixed search policy compares LLM-, expert-, generic-, and ablated-space
  sources so search-space and search-policy effects are not conflated.
- Real candidate verification and EDA outcomes provide downstream utility
  authority.

Permitted claims concern bounded reference recall, valid additional
opportunities, and downstream utility. Completeness and global optimality are
not claimed.

### D25. Skeleton-supported child architecture preservation (confirmed 2026-09-11)

Deterministic skeletons and associated checkers may protect a sealed child's
architecture during repair. Distinguish three levels: accepted user obligations
that all candidates preserve; child-specific architecture decisions preserved
during repair but changeable in a subsequent architecture mutation; and
implementation details editable within those boundaries. Do not freeze every
possible architecture variable across the entire search.

The candidate protection scope includes module partitioning, interfaces and
connectivity, FPGA placement of functional roles, clock/reset and CDC structure,
state/storage ownership, parallelism and resource sharing, pipeline/scheduling
boundaries, buffering/flow control, accepted numeric constraints, and project/
edit boundaries. Applicability and protection mechanisms must be specified per
decision. Skeleton structure alone does not establish behavioral correctness,
resource sharing, CDC safety, or numeric fidelity; qualified structural and
behavioral checks must support each claimed invariant. An unverified invariant
cannot receive architecture-preservation credit.

The LLM may propose open RTL implementations and new architecture mutations;
this does not require a complete family-specific RTL template library. Seal the
decision and its protected boundaries before repair. Repair creates a new child
with parent/patch/artifact lineage; it does not overwrite the failed candidate.
A change to the sealed architecture is classified as an architecture change, not
successful preservation by repair, and must follow the declared mutation
admission process rather than bypass it. Every repaired candidate repeats the
required public validation and QoR evaluation, with repair costs retained.
This is a design decision, not a claim that current skeletons implement these
protections. Exact checkers, invariants, artifact/schema definitions, and mutation
reclassification handling remain open. It does not authorize code/contracts,
canonical v1.8, LaTeX, implementation, model, pilot, or experiment changes.

### D26. Stop non-preserving repair branches (confirmed 2026-09-11)

the decision and claim successful architecture-preserving recovery. This does

Exact repair caps, detection and stopping criteria, and shared search-budget

### D27. Dual repair-budget boundaries (confirmed 2026-09-11)

budget. Reaching either limit stops the repair branch. Exhausting only the
branch allowance permits EA to continue from eligible feasible parents while
common budget remains; exhausting the common budget stops further optimization.
Repair costs and failed attempts remain recorded. Exact budget units, allowance
values, accounting boundaries, and enforcement details remain open. This
decision concerns optimization-stage repair, not the still-open generation-stage

### 四、实验回答的问题

1. 空间有没有价值：专家预封存机会参照、open-set 评价、空间基数/覆盖/重复与
