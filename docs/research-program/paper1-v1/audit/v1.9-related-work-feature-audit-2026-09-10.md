## Executive verdict

The following ideas are already occupied and cannot anchor an independent
novelty claim:

1. LLM-generated Verilog combined with population-based evolutionary search;
2. idea/thought plus code as a multi-representation evolutionary individual;
3. dual or staged handling of functional failure and PPA improvement;
4. nondominated/Pareto selection for LLM-generated hardware;
5. iterative synthesis-feedback RTL optimization;
6. conversational user-guided RTL DSE;
7. repository-level hardware evolution under an executable harness;
8. evolutionary HLS generation followed by repair and real-board execution;
9. cost-aware reasoning-effort steering for RTL optimization; and
10. expert/compiler-defined FPGA design spaces searched by EA, RL, BO, or
    hybrid surrogate methods.

The strongest remaining candidate contribution is the joint treatment of:

> provenance-typed completion of non-expert requirements; an explicit LLM-
> generated Design-Space Contract; independent presealed/open-set evaluation of
> that contract's architecture opportunities; contract-guided open RTL mutation
> over complete FPGA Project Packages; opportunity-to-outcome lineage; and a
> repair-visible public evaluator separated from one-shot hidden terminal
> authority.

No audited work combines all of those features in its reported experiment. This
is a bounded audit conclusion, not a universal or permanent `first` claim.

## Per-work audit

### 1. EvoVerilog

**Identity and scope.** EvoVerilog is an arXiv 2025 preprint that evaluates
module-level Verilog generation on VerilogEval-Machine/Human. It does not start
from a complete FPGA project, target profile, project constraints, or user-
negotiated requirement envelope.

**Representation and search.** It first constructs an idea tree, samples natural-
language or other indirect representations, generates aligned Verilog, and then
uses a population EA. Positive/negative crossover and mutation generate
offspring; nondominated sorting jointly minimizes testbench mismatch and
wire/cell counts. This directly occupies LLM idea-plus-code evolution,
population search, multi-representation initialization, and nondominated
hardware selection.

**Evidence boundary.** Primary results are pass@1/5/10; resource analysis counts
wires and logic cells and reports very few nondominated designs. The paper
itself observes that VerilogEval commonly has one resource-efficient solution,
making it weak for architecture-diverse DSE. No synthesis, P&R, hidden terminal
evaluation, complete-project output, or explicit LLM-generated search-space
contract is reported. Prompt changes materially alter reproduced baselines.

**SR2FPGA role.** Mandatory Related Work and direct evolutionary-generation
neighbor; adapted baseline only if a stable implementation is located. SR2FPGA
cannot claim first LLM+EA Verilog generation, idea/code co-representation, or
Pareto selection. Remaining distinction is explicit requirement-conditioned DSC
generation/authority, FPP-level artifacts, real FPGA QoR, and hidden terminal
separation. Source: [official full text](https://arxiv.org/html/2508.13156).

### 2. REvolution

**Identity and scope.** REvolution is accepted at ASP-DAC 2026 and evaluates
module-level Verilog generation on VerilogEval v2 and RTLLM-2.0.

**Representation and search.** Each individual is `(Thought, Code, Feedback)`.
An initial LLM population is split into Fail and Success populations. Fix,
Simplify, Explore, Refactor, Improve, and Fusion prompts act as evolutionary
operators; UCB/softmax adapts operator choice. Incorrect individuals receive
negative-infinite fitness; correct individuals use a manually weighted relative
power/area/effective-clock score.

**Repair and evidence.** Fail candidates receive bug-fixing feedback and Success
candidates receive PPA feedback. Icarus simulation and Yosys/Nangate45 synthesis
provide visible feedback. Final pass rate, conditional PPA improvement, and
runtime are reported; PPA excludes small and non-synthesizable-reference cases.
There is no separate hidden terminal evaluator, explicit DSC, project-package
contract, FPGA P&R, or board evidence.

**SR2FPGA role.** Highest-priority adapted baseline because a public ASP-DAC
release tag is linked. Its native result should first be smoke-reproduced; the
FPGA adapter must be named `REvolution-adapted`. SR2FPGA must isolate the gain
from DSC/authority rather than from the already occupied dual-population,
repair, fusion, and adaptive-prompt machinery. Source:
[official full text](https://arxiv.org/html/2510.21407).

### 3. EvolVE

**Identity and scope.** EvolVE is a 2026 preprint. It evaluates functional
generation on VerilogEval v2, Mod-VerilogEval v2, and RTLLM v2, and PPA on the
new IC-RTL suite.

**Representation and search.** Idea-Guided Refinement creates multiple high-
level architecture ideas and independent refinement chains; MCTS instead grows
a scored code tree. Structured Testbench Generation supplies a dense functional
score. The framework uses a 300-node budget, with IGR configured as 60 ideas by
five refinements and MCTS using tree expansion.

**Endpoint and toolchain.** Functional generation uses pass rate across tests
and benchmark pass at node budgets. PPA requires all tests to pass and optimizes
negative Area x Latency; IC-RTL results are validated with commercial synthesis
and timing/power tools. No explicit DSC, independent design-space authority,
complete project package, final hidden separation, or FPGA P&R/board result is
reported.

**SR2FPGA role.** Strong search-strategy reference and optional adapted baseline.
Its released IC-RTL benchmark is more immediately reusable than the complete
framework. SR2FPGA cannot claim first LLM idea-guided architecture exploration,
MCTS hardware-code search, or node-budgeted search. Source:
[official full text](https://arxiv.org/html/2601.18067).

### 4. POET

**Identity and scope.** POET is a March 2026 preprint for RTL-to-RTL PPA
optimization over 40 RTL-OPT designs. It starts from an existing correct RTL
design, not a natural-language project request.

**Verification and evolution.** The original design is used as a deterministic
functional oracle to generate differential test vectors and golden outputs.
Population evolution uses LLM mutation/crossover, capped repair, nondominated
sorting, power-first intra-front ranking, and proportional allocation. Every
surviving individual is testbench-passing.

**Endpoint and boundary.** The paper reports functional pass counts and the
number of designs attaining best power, area, and delay; it does not report
archive hypervolume. Evaluation uses Icarus, Yosys equivalence, Yosys/OpenSTA,
and Nangate45. It has no requirement completion, explicit generated design
space, FPGA P&R, project package, or hidden-final authority. Its generated
testbenches were manually inspected, and no implementation link was found in
the audited full text.

**SR2FPGA role.** Methodologically strongest Track-O reference and conditional
adapted baseline. The common experiment must give both methods the same verified
seed and final evaluator; SR2FPGA cannot attribute ordinary Pareto evolution or
differential RTL checking to DSC. Source:
[official full text](https://arxiv.org/html/2603.19333).

### 5. CRADLE

**Identity and scope.** CRADLE is accepted at ISOCC 2025. It takes existing
hierarchical RTL and testbenches plus a conversational user optimization goal.

**Method.** A generator--critic agent system uses Yosys and nextpnr reports to
plan and rewrite RTL, and ModelSim plus the supplied testbench for correction.
The evaluated flow runs at most three internal iterations and returns the best
resource result. It is conversational and user-guided but not a population EA,
and it does not materialize an explicit design-space artifact.

**Evidence.** On RTLLM reference implementations mapped to Lattice ECP5, the
paper reports best-variant LUT/FF reductions. It does not provide timing/power,
multi-objective archive quality, a hidden evaluator, requirement completion,
DSC authority, or a complete new project. The full text links build logs, but a
stable framework source release was not established in this audit.

**SR2FPGA role.** Mandatory published conversational-RTL-DSE baseline/reference.
An adapter is fair only in an existing-RTL optimization track. SR2FPGA's user-
facing Harness and FPGA resource loop are not independently novel; the remaining
distinction is explicit generated space/authority, population EA, FPP output,
and hidden terminal separation. Source:
[official full text](https://arxiv.org/html/2508.08709).

### 6. HINT

**Identity and scope.** HINT is an August 2026 preprint and the closest
executable-intent representation neighbor. It converts specifications/reference
behavior into one accepted microarchitecture artifact and lowers it to RTL.

**Representation.** HINT makes interface, state, schedule, resources, and
lowering obligations explicit. A case-independent lint checker validates form;
transaction-level checking evaluates the artifact before RTL lowering. This is
an executable architecture contract, not a search-space contract and not an RTL
template.

**Evidence.** The controlled study stops at the first successful synthesis after
correctness acceptance. Total cell area is the primary metric under fixed
constraints; critical-path delay and ADP are supplementary. Seven operator
cases, RealBench AES/SDC, and a Vortex-derived VPU provide bounded cross-scale
evidence. Only one case receives netlist Formality; the others use transaction-
level regression. There is no EA, DSC adequacy evaluation, Pareto archive, FPGA
P&R, board run, or public/hidden terminal split.

**SR2FPGA role.** Mandatory representation reference, not a same-algorithm
baseline. SR2FPGA cannot claim first executable hardware-intent layer,
pre-RTL architecture acceptance, or checked intent-to-RTL lowering. Its
remaining distinction must be search-space generation/authority and FPP-level
evolution. Source: [official full text](https://arxiv.org/html/2608.07625).

### 7. HORIZON

**Identity and scope.** HORIZON is a June 2026 preprint with an existing complete
local reader/evidence card. A human supplies a structured Markdown harness; a
bootstrap agent compiles it into a project pack; a hands-free agent evolves an
isolated git worktree.

**Control plane and output.** The project pack contains the policy prompt,
evaluator, acceptance predicate, git/artifact policy, and domain skills. Git
worktrees, diffs, accepted commits, rejected attempts, notes, and evaluator
outputs provide repository-native lineage. This is a task control plane, not a
typed hardware requirement/architecture contract.

**Evidence boundary.** HORIZON reports single-campaign best-so-far completion,
coverage, and token trajectories on ChipBench, RTLLM, VerilogEval, and selected
CVDP categories. The same visible benchmark harness guides repair and acceptance.
The paper explicitly identifies hidden/randomized final scoring as future work.
It does not report a PPA search campaign, uniform complete-FPGA-project contract,
DSC generation/authority, repeated-run uncertainty, or released project
packs/raw traces at the local evidence cut.

**SR2FPGA role.** Mandatory repository-harness closest work but currently a
reference rather than runnable baseline. Repository evolution, git lineage,
executable acceptance, and hands-free multi-round repair are occupied. The
candidate distinction is hardware-semantic DSC plus multi-objective FPP search
and mechanically separated final authority. Sources:
[official full text](https://arxiv.org/html/2606.28279) and
[local evidence card](</D:/Obsidian Vault/博士开题/硬件代码生成/SR2FPGA-TCAD/01_literature/evidence-cards/horizon.md>).

### 8. FPGAgent

**Identity and scope.** FPGAgent is an August 2026 preprint that starts from a
natural-language HLS task plus interface header and targets Xilinx U200. It is
the strongest end-to-end FPGA deployment threat in the audited set.

**Search and repair.** An assistant retrieves official Vitis optimization
strategies, generates an enlarged initial kernel pool, and uses Exploration and
Modification operators over a population. Vitis simulation filters candidates
and latency/resource performance selects survivors. A separate Functional
Reflection stage generates C++ tests, diagnoses errors, and repairs HLS code.
Host-code compilation/runtime errors receive another repair loop backed by
canonical failure examples.

**Physical endpoint.** The deliverable is a compiled FPGA executable with host
code, executed and functionally checked on a U200 board. The main outcomes are
synthesizable, executable, and functional-correctness rates relative to a
zero-shot pass@10 baseline. The paper acknowledges that performance optimization
remains future work despite using latency/resource information internally.

**Boundary and reproducibility.** There is no explicit requirement-completion
contract, LLM-generated DSC, independent DSC adequacy authority, Pareto archive,
or hidden terminal evaluator. Seventy-eight of 94 HLS-Eval tasks are retained
after interface adjustments. Source code and reproduction artifacts are promised
after acceptance rather than available in the audited paper.

**SR2FPGA role.** Mandatory cross-abstraction reference; not a direct RTL
baseline. SR2FPGA cannot claim first natural-language evolutionary FPGA code
generation, separate repair, host generation, executable build, or real-board
validation. Source: [official full text](https://arxiv.org/html/2608.23630).

### 9. FinHardBench

**Identity and scope.** FinHardBench is a COLM 2026 conference paper and open
benchmark. It contains 33 financial FPGA module tasks, a fixed six-stage system
DSE, and 15 specification-adaptation tasks.

**Three experiment types.** Module generation is single-shot specification-to-
Verilog. System DSE exposes a benchmark-authored 432-configuration space; the
LLM chooses one configuration per round from performance history, without
writing code. Adaptation gives existing RTL, timing, and a changed specification
for three feedback rounds.

**Evaluation.** Icarus, Yosys, and nextpnr/ECP5 provide a consecutive syntax--
simulation--synthesis--route chain, Fmax, LUTs, and domain-specific critical-path
delay. The DSE objective minimizes a structural six-stage latency expression
under a 5000-LUT budget and compares five seeds over 24 rounds against random,
simulated annealing, and TPE Bayesian optimization. A 13-design Vivado/Kintex
subset checks rank transfer. There is no independent final hidden evaluator;
the system model omits queue fill, stall propagation, and data-dependent timing.

**SR2FPGA role.** Strong published benchmark and classical-search comparator,
especially for RQ2. It occupies LLM feedback-based FPGA configuration search,
fixed-budget random/SA/BO comparison, post-P&R timing, and specification
adaptation. It does not generate its search space, evolve RTL in the system DSE,
evaluate DSC adequacy, or output an evidence-bearing FPP archive. Source:
[official full text](https://arxiv.org/html/2608.00909).

### 10. Dr. RTL

**Identity and scope.** Dr. RTL is an April 2026 preprint with a locally audited
public artifact. It optimizes existing human-written RTL/IP under commercial
synthesis and equivalence checking; it is not requirement-to-project synthesis.

**Search and memory.** A timing agent maps critical paths back to RTL, a rewrite
agent generates five candidates per round, and an evaluator runs synthesis and
SEC. The best SEC-passing scalar-score candidate becomes the next parent. Group-
relative comparison distills trajectories into a 47-entry pattern--strategy
skill library reused across designs. This is parallel greedy search plus external
skill learning, not population EA.

**Evidence.** Twenty designs, ten rounds by five candidates, WNS/TNS/area,
SEC-pass rate, convergence, approximate LLM cost, and a reported post-route
subset are evaluated. Power is excluded because workload-dependent static power
estimation is considered unreliable. No hidden terminal evaluator or requirement
contract exists. The release lacks raw optimized RTL/trajectory/report artifacts,
and its LSTM path uses simulation where the paper broadly describes SEC.

**SR2FPGA role.** Conditional strong Track-O baseline and mandatory memory/
industrial-tool reference. It occupies fine-grained critical-path feedback,
parallel same-parent rewriting, commercial SEC, cross-design skill extraction,
and realistic human-written RTL optimization. Sources:
[official full text](https://arxiv.org/html/2604.14989) and
[local evidence card](</D:/Obsidian Vault/博士开题/硬件代码生成/SR2FPGA-TCAD/01_literature/evidence-cards/dr-rtl.md>).

### 11. Ares

**Identity and scope.** Ares is a July 2026 preprint for cost-aware RTL-to-RTL
PPA optimization. It starts from functionally correct RTL and a testbench and
maintains one running-best design rather than a population.

**Method.** The objective is normalized area x power x delay. Every candidate is
checked against the input design with fixed random vectors, RTL sequential
equivalence, synthesis, and post-synthesis simulation. A patience counter fitted
on 21 training designs escalates per-call reasoning effort after stalled or
failed progress; three designs are held out for policy evaluation.

**Cost and comparison.** Ares prices each LLM call in normalized high-effort-call
units and compares FoM versus cumulative dollar cost. It adapts released
REvolution and Dr. RTL to one commercial flow on the same starting RTL and 25
candidates. This is a particularly relevant precedent for naming adapted
baselines and for reporting cost rather than generation count alone.

**Boundary.** It has no requirement completion, generated DSC, population EA,
FPGA P&R, complete project package, or hidden-final authority. Only REvolution
and Dr. RTL are identified as released comparison implementations in its audit;
no Ares repository link appears in the paper.

**SR2FPGA role.** Mandatory cost-protocol and reasoning-effort reference;
conditional baseline only after artifact release. SR2FPGA must record actual
tokens/provider price and cannot call equal candidate counts equal economic
budget. Source: [official full text](https://arxiv.org/html/2607.27879).

### 12. AutoDSE

**Identity and scope.** AutoDSE is a peer-reviewed ACM TODAES 2022 paper with a
public BSD-3-Clause repository. It starts from HLS C/C++ and a compact Merlin
pragma space, not natural-language RTL generation.

**Space and search.** Merlin directives expose parallelism, fine/coarse pipeline,
tiling, and related architecture transformations. AutoDSE represents valid and
invalid grid points, partitions the space, detects tool-reported bottlenecks, and
uses coordinate/bottleneck-guided optimization. The formal objective minimizes
estimated cycles under FPGA resource thresholds.

**Evidence.** The work reports speedup, gap to manual HLS designs, and reduction
in manually inserted pragmas; its fast mode uses HLS synthesis and accurate mode
can build the bitstream. The space remains compiler/expert defined, functional
semantics come from HLS C, and there is no LLM, requirement completion, hidden
evaluator, or explicit search-space adequacy authority.

**SR2FPGA role.** Strong published cross-paradigm reference, not a direct fair
RTL baseline. Its optimizer may be reused only on overlapping HLS tasks or as a
bottleneck-guided policy over a frozen DSC. Source:
[official full text](https://arxiv.org/html/2009.14381) and
[ACM article](https://doi.org/10.1145/3494534).

## Published traditional-DSE anchors

These works constrain algorithm novelty but need not be rerun as LLM-Harness
baselines:

- **IronMan** combines a GNN resource/performance predictor, RL multi-objective
  DSE, and HLS code transformation; it reports Pareto/constraint outcomes and
  comparisons with GA/SA. It is published at GLSVLSI 2021, DOI
  `10.1145/3453688.3461495`.
- **Chimera** combines active learning, evolutionary search, and Thompson
  sampling to recover HLS Pareto designs with few evaluated points. Its arXiv
  version extends an IDEAL 2021 Best Paper.

Consequently, neither use of EA for FPGA DSE, Pareto discovery, surrogate-
assisted search, nor GA/SA/BO comparison is independently novel. Sources:
[IronMan](https://arxiv.org/abs/2102.08138) and
[Chimera](https://arxiv.org/abs/2207.07917).

## Cross-work findings

### F1. The closest collision is a four-way combination

No single prior system exactly matches v1.9, but four works collectively occupy
most generic wording:

- EvoVerilog/REvolution/POET occupy LLM population evolution, repair, and
  Pareto/PPA optimization;
- CRADLE occupies conversational FPGA RTL DSE;
- HORIZON occupies executable harness plus repository evolution and lineage;
- FPGAgent occupies natural-language evolutionary FPGA generation, repair,
  executable construction, and board validation.

The paper cannot claim novelty by listing those components independently. It
must test the requirement-conditioned DSC/authority/opportunity-closure
combination.

### F2. Explicit search-space generation remains the best opening

Prior LLM evolution systems use implicit spaces expressed by prompts, ideas,
parent code, strategies, or benchmark-authored knobs. HINT explicitly represents
one microarchitecture, while AutoDSE and FinHardBench expose spaces authored by
compiler/benchmark designers. In the audited scope, none generates a first-class
DSC from non-expert intent and independently evaluates the quality of that DSC.

This opening is defensible only if SR2FPGA measures the generated space itself:
presealed opportunity recall, open-set novel yield, legal/unique realization,
and opportunity-to-outcome closure. Merely serializing LLM suggestions as JSON
would not create a contribution.

### F3. Complete-project language must remain precise

HORIZON evolves repository states, and FPGAgent generates kernel/host executables.
SR2FPGA therefore cannot use `project`, `harness`, or `end-to-end` alone as a
novelty marker. The exact FPP contract must require RTL sources, constraints,
manifest, target/build metadata, protected evaluator boundaries, verification
evidence, QoR artifacts, and lineage. Whether bitstream or board output is
mandatory must be stated separately.

### F4. Hidden terminal separation is still differentiating

The audited LLM methods expose their evaluator/testbench or tool diagnostics
during generation, repair, or optimization. HORIZON explicitly identifies final
hidden scoring as future work. FinHardBench withholds tests from the model in
single-shot generation but does not implement a repair-visible public search
followed by a separate one-shot hidden terminal authority. This remains a strong
protocol distinction if implemented mechanically and evaluated rather than
described only in prose.

### F5. Search-space and search-policy effects must be separated

Comparing SR2FPGA's LLM-generated DSC plus LLM-EA against another method with a
different space and policy cannot identify why it wins. The required factorial
logic is:

1. hold DSC fixed and compare random/SA/BO/conventional EA/LLM-local/LLM-EA;
2. hold search policy fixed and compare LLM/expert/generic/ablated spaces;
3. treat direct phenotype and external systems as bundle comparisons.

### F6. Cost matching must be multi-view

REvolution reports average runtime, EvolVE reports node/token efficiency,
HORIZON reports cached-token trajectories, and Ares shows that call count can
hide reasoning-effort price. SR2FPGA must predeclare candidate, logical-call,
token, simulation, synthesis/P&R, EDA-time, wall-time, and actual API-cost views.
Only one can be the primary stopping budget; the rest remain mandatory reports.

### F7. Verification strength is heterogeneous

Testbench simulation, differential testing, CEC, SEC, transaction-level
co-simulation, P&R, and board execution establish different claims. A common
final evaluator is required for adapted baselines. Method-native checks may
remain inside each method as part of its bundle but cannot serve as the common
final authority.

## Required changes to the v1.9 candidate protocol

Before propagation, v1.9 must:

1. add EvoVerilog, CRADLE, FPGAgent, FinHardBench, Dr. RTL, Ares, REvolution,
   POET, EvolVE, HINT, HORIZON, and AutoDSE to the formal feature matrix;
2. replace generic `first` language with bounded combination-level positioning;
3. split generation and existing-seed optimization tracks;
4. make REvolution the priority runnable evolutionary baseline and CRADLE the
   priority published conversational RTL-DSE comparator;
5. include random, SA, BO/TPE, conventional EA, and LLM-local refinement under
   a frozen DSC;
6. isolate DSC-source effects with fixed-policy `SPACE-LLM`, `SPACE-EXPERT`,
   `SPACE-GENERIC`, and `SPACE-ABLATE` comparisons;
7. add Ares-style actual cost accounting and a declared primary stopping budget;
8. state that HORIZON already occupies repository harness/git evolution;
9. state that FPGAgent already occupies evolutionary HLS-to-board generation;
10. preserve one-shot hidden terminal evaluation as a required, implemented
    distinction; and
11. require a complete FPP contract rather than relying on `project` language.

## Candidate novelty statement after audit

The strongest currently supportable positioning is:

> SR2FPGA studies design-space construction itself as a requirement-conditioned
> hardware-generation problem. Its Harness separates user facts, derived
> obligations, proposed defaults, architecture freedoms, and unresolved
> semantics; asks an LLM to produce an explicit DSC; independently evaluates
> that DSC against presealed and open-set architecture opportunities; evolves
> concrete RTL patches as complete evidence-bearing FPGA Project Packages; and
> separates repair-visible public search from one-shot hidden terminal
> validation.

This is a candidate combination claim. Effectiveness, scalability, cost, and
superiority remain untested.

## Stop condition and limitations

- This audit read complete accessible paper text for the twelve core works but
  did not execute any external repository or commercial EDA flow.
- Local full reader/evidence-card chains already exist for HORIZON and Dr. RTL;
  HINT has local source-verified evidence. The newly audited web-full-text works
  still require local PDF hashes/evidence cards before becoming `claim-ready`
  under the Paper-1 citation registry.
- Code availability was classified only from paper/arXiv links and existing
  local artifact audits; absence of a located link is not proof that no code
  exists elsewhere.
- Publication status and artifacts can change before submission. A final
  literature/status refresh is mandatory immediately before protocol freeze and
  manuscript submission.
